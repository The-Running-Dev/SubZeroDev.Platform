# Design — commercial (D5)

Written from [`00-brief.md`](00-brief.md). Nine capabilities — Identity, Authorization,
Organizations, Tenancy, Billing, Licensing, Audit, shared web UI and `Platform.Mcp` — reduced to the
smallest set of seams that serves four named consumer shapes without any of them being present.

**What this document does not restate.** The tenant identifier, the tenant column, the operation
scope, the result and error types, the module contract, the transaction abstraction, the outbox, the
lease, the settings fingerprint and the redaction boundary all exist in the tree and are cited, never
re-specified — `AGENTS.md`, *Single ownership*, "A document states only what the tree cannot". Where
this design changes one of them, it says which file and why.

**The one idea the rest of the document is generated by.** [ADR-006](../docs/docs/adr/ADR-006-application-modules.md)
rule 1 forbids a framework package referencing a module, and rule 2 forbids a module referencing
another module. D5's capabilities are coupled in use — Authorization must audit, Mcp must authorize,
Organizations must provision tenants, Billing and Licensing must both answer one entitlement question
— so under those two rules there is exactly one shape that works:

> **The framework owns the questions and the composition. Modules own the answers.**

Every commercial capability splits into a *decision seam* that lives in the framework and a *policy
store* that lives in an opt-in module. A seam has a default answer that is correct with every module
absent, which is what makes the identity-free, billing-free, licence-free local shape a real
composition rather than a set of checks that pass. A module contributes answers to seams; it never
reaches another module. That keeps rule 2 vacuous by construction rather than by discipline.

The rule that stops this from becoming "put everything in the framework" is stated and applied in
*Module boundaries*, § **The seam-admission test**.

## Data model

### 1. What is persisted, and by whom

Nothing in the framework's D5 additions is persisted except audit, and audit's storage is a module.
That is the single most consequential property of the model, and it is what the brief's local shape
forces: a host with no Identity, Organizations, Billing or Licensing package has no table those
capabilities would own, and no migration to skip.

| Owner | Persisted | In-memory only |
|---|---|---|
| Abstractions | — | principal, principal id and kind, permission name, feature name, authorization decision, entitlement decision, audit event, composition profile |
| Persistence | the shareable marker on entity types that declare it | the shared-read scope |
| Audit store module | the audit record | — |
| Organizations module | organization, membership, invitation | active-organization selection (per request) |
| Billing module | plan, subscription, provider event receipt | entitlement (derived) |
| Licensing module | the verified-licence record | licence claims (derived), grace state (derived) |
| Mcp module | — | tool registration and exposure, frozen after startup |
| Web shell | — | everything; it holds no state the backend does not |

### 2. Identity — the principal is total

`ICurrentPrincipal.Current` is `ClaimsPrincipal?` today
([`src/SubZeroDev.Platform.Abstractions/OperationContext.cs`](../src/SubZeroDev.Platform.Abstractions/OperationContext.cs)),
and `IAuditable.CreatedBy` is `string?` for the same reason — D3 had no identity, so it had no actor.
**D5 makes the ambient principal non-null**, exactly as `TenantId` is already non-null with a
well-known implicit value. There is always an actor; "no principal" is a kind of principal, not the
absence of one.

The nullable form is what makes audit unfalsifiable: a record whose actor column is empty cannot be
distinguished from a record whose actor was never resolved, and the brief requires that allowed,
denied and failed actions each name an actor. A well-known anonymous principal costs one constant and
removes that hole permanently.

**`PrincipalId` is a pair — issuer and subject, both opaque strings, compared ordinally.** Not a
single string. Brief decision 5 keeps the Automator and Game Engine identity stores separate and
preserves a later reversal without requiring it; a single-string id makes that reversal a data
migration the first time two stores mint the same subject. The pair costs nothing now and is the only
part of the identity model that is expensive to add later.

Neither half is parsed, normalised or case-folded by Platform. Opacity is the point: the moment
Platform knows what a subject looks like, it has an opinion about which providers are legal.

**Four kinds, and the kind is what decides whether the actor is resolvable afterwards.**

| Kind | Established by | Directory | Consumer shape it exists for |
|---|---|---|---|
| `Anonymous` | nothing | none | an unauthenticated public read |
| `Account` | an authentication provider that can be asked about the subject later | yes | Automator operators, GEaaS players |
| `Delegated` | an assertion from a boundary Platform trusts but does not own — an upstream proxy header, a capability link | no | SkyNet HR's proxy-asserted operator, BarStrad's QR-established table |
| `System` | Platform itself | n/a | `system:local`, background work acting on its own behalf |

`Delegated` is the kind the brief's "accountless principal" names, and it is not a degraded
`Account`. [`docs/docs/application-modules.md`](../docs/docs/application-modules.md) §2 states the
correction directly: a principal need not be an account, and no account will ever exist for
BarStrad's customer-side principal. Modelling it as an `Account` with missing fields makes every
consumer of the principal defensive about fields that are permanently absent.

`Principal` carries its id, its kind, an optional display name and the claims the authentication
provider produced. It is derived per request and never persisted; only the `PrincipalId` reaches
storage, through the existing audit columns.

**Nothing in Identity is a user table.** The brief's Identity row commits to "integration seams for
hosted authentication without choosing or owning an identity provider", and the non-goals rule out
federation, account linking and a shared directory. Platform therefore has no user entity, and the
Identity module is authentication providers and principal mapping — no rows.

### 3. Authorization — names, providers, decisions

**`PermissionName` is a stable string id** in the `<Product>.<Area>.<Action>` form
[`platform-specification.md`](../docs/docs/platform-specification.md) already fixes. Platform's own
permissions take the `Platform.` prefix. Names are registered at startup by whichever module
contributes them; an unregistered name reaching the evaluator is a startup-detectable defect, not a
runtime denial, because a typo that silently denies is indistinguishable from a policy that denies.

**A grant is contributed, never stored by the framework.** The evaluator asks every registered
permission provider and takes the union. D5 ships exactly two providers, and neither is a
role-assignment table:

- the **composition provider**, which grants the local operator every permission in the `Local`
  profile and nothing at all in `Operated`;
- the **Organizations provider**, which derives grants from a membership's role.

The consequence worth stating: **D5 has no role-assignment store**, and the brief does not ask for
one. Roles are a closed set on the membership — owner, administrator, member — because teams and
richer organization administration are explicit non-goals. A consumer needing custom roles registers
a third provider; that is the extension point, and it needs no Platform table.

**`AuthorizationDecision`** carries the permission, the resource when the check was resource-scoped,
the tenant it was evaluated in, the outcome, and **the provider that produced the grant**. The last
field is not diagnostics. The evaluator takes a union across providers, so a wrong grant is a wrong
*provider*, and a decision that cannot name its source cannot be traced back to one.

### 4. Tenancy — the escape is a scope, not a flag

The tenant identifier, its implicit value, its presence in every primary key and the store's supply
of the constant are settled and are not touched: `TenantId` in
[`src/SubZeroDev.Platform.Abstractions/Identity.cs`](../src/SubZeroDev.Platform.Abstractions/Identity.cs),
`ITenantOwned` in
[`src/SubZeroDev.Platform.Persistence/Columns.cs`](../src/SubZeroDev.Platform.Persistence/Columns.cs),
and the brief's *Tenancy inherited from D3 and G2*. D5 adds two things to it and nothing else.

**First, resolution.** `ICurrentTenant` exists and always answers `TenantId.Implicit` because nothing
resolves one. D5 registers tenant resolvers at the request boundary; with none registered the answer
is unchanged, which is what makes local mode identical to today rather than a special case.

**Second, the deliberately shared resource.**
[`second-consumer-packages.md`](../docs/docs/second-consumer-packages.md) §3 names this as the thing
to design, "because an unmodelled one is how isolation quietly stops holding." Three properties are
required of it, and they decide its shape between them:

1. **Shareability is a property of the type, declared at model build.** An entity type either
   declares itself shareable or it does not, and the declaration is visible in the model. A per-row
   flag on an ordinary type is refused: it makes the isolation boundary writable by any code path
   that can write the row, which is the failure mode inverted.
2. **A row becomes shared through an explicit, permissioned, audited write** that stamps a shared-at
   instant. That write is an ordinary tenant-scoped write by the owning tenant — publication is
   something a tenant does to its own row — so nothing about it crosses a boundary.
3. **A cross-tenant read happens only inside a named scope, and the scope is read-only.** Outside the
   scope the query filter is `tenant equals current`, unconditionally, for shareable and
   non-shareable types alike. Inside it, and only for the one declared type the scope names, the
   filter widens to "mine, or shared". **A write attempted inside a shared-read scope is a contract
   violation and throws** — the same class as
   `ContractViolation.NoAmbientTransaction` in
   [`src/SubZeroDev.Platform.Abstractions/Results.cs`](../src/SubZeroDev.Platform.Abstractions/Results.cs).

The invariant that falls out is the one worth having: **there is no code path in Platform by which a
write reaches another tenant's row.** Isolation is asymmetric on purpose. Reads have one modelled,
audited escape; writes have none.

Opening the scope emits one audit event, not one per row. A published-campaign listing that returns
four hundred rows is one escape, and four hundred audit records would make the audit trail unreadable
at precisely the point it matters.

### 5. Organizations — a module, and the only thing that mints a tenant

`Organization` holds its own identity, the tenant it provisioned, a name, its creation instant and
its owner. `Membership` holds the organization, a `PrincipalId`, a role and a state. `Invitation`
holds the organization, the role it confers, an expiry, **a hash of the invitation token and never
the token**, and the principal and instant that redeemed it.

Three decisions in that paragraph are load-bearing.

**The organization holds a tenant id; it is not one.** One organization has exactly one tenant, minted
when the organization is created, and the framework never learns that a tenant has an owner. Making
the organization id *be* the tenant id is one fewer column and was rejected: it puts a module's
identity into a framework type, so the framework's tenant would then mean "an organization", and a
later consumer wanting more than one tenant per organization would face a migration rather than an
added column. The indirection costs one join in the Organizations module and buys the whole of that.

**Membership is keyed by `PrincipalId`, which is a framework type.** This is what keeps Organizations
free of any reference to Identity — rule 2 — and it is also what lets a `Delegated` principal hold a
membership. A membership that referenced a user row would exclude BarStrad's table and SkyNet HR's
proxy-asserted operator by construction.

**An invitation is a capability, and D5 mints and redeems it but does not deliver it.** Delivery is
Notifications, which is D4 and is not in this effort. The token is returned once at mint and never
readable again; only its hash is stored, so a database read cannot be replayed into a membership. The
brief's Organizations criterion — one principal invites, a second accepts — is satisfied by mint and
redeem, and nothing in it requires an email to be sent.

The *active organization* is a per-request selection, not a stored preference. It resolves to a
tenant through the Organizations tenant resolver, and a selection naming an organization the
principal is not a member of resolves to nothing — see *Failure modes*, § **Existence is not
confirmed to a caller who may not see it**.

### 6. Billing and Licensing — two stores, one seam

**`FeatureName` is the entitlement question, and it is the only one product code asks.** The brief
forbids product code reading subscription state, and
[`tenancy-billing-licensing.md`](../docs/docs/tenancy-billing-licensing.md) forbids any code path
outside the billing module branching on it. Licensing answers the same question from a different
source. A design with two queries — "is the subscription active" and "does the licence grant this
tier" — puts the branch back into product code under a different name, so **Billing and Licensing
contribute to one entitlement seam and neither is queryable directly.**

Contribution is a **union**: any registered contributor granting a feature grants it, and the
`EntitlementDecision` records which contributor did. Intersection was rejected — installing Licensing
into an operated SaaS deployment would silently revoke subscription entitlements, which is a failure
mode nobody would look for. The union's own risk, that one wrong contributor grants everything, is
bounded by the decision naming its source, by the contributor set being registered explicitly and
enumerated at startup, and by the contributor set joining the settings fingerprint
([`src/SubZeroDev.Platform.Core/SettingsFingerprint.cs`](../src/SubZeroDev.Platform.Core/SettingsFingerprint.cs)),
so two instances that disagree about who may grant are visible through the existing
`platform.settings-fingerprint` check rather than by their behaviour diverging.

**Billing.** `Plan` carries a stable key, a display name and the set of features it grants.
`Subscription` carries its tenant, its plan, a state, the period boundaries, an optional trial end and
an opaque provider reference. Entitlement is **derived** from the plan and the subscription's state
against the clock — never stored, so a plan transition takes effect by changing one row rather than by
a fan-out that can be interrupted.

The seam to a provider is **asynchronous, and it is asynchronous now even though D5 integrates no
provider.** A provider's authoritative state arrives as an inbound event that updates the stored
subscription; entitlement always reads stored state. Real payment providers are webhook-driven and
eventually consistent, and a synchronous seam — "ask the provider whether this account is paid up" —
is a rewrite when the first real one arrives and a network call on the request path in the meantime.
Who delivers the event, a webhook or a poll or an operator, is out of scope; that the seam accepts one
is not. `ProviderEventReceipt` records the provider's event identity so a redelivered event is
idempotent, which every provider requires and none guarantees.

**Licensing.** The licence document is an input file and is never persisted by Platform. What is
persisted is one `VerifiedLicence` row for the installation, holding the tier, the granted features,
the issue instant, **the expiry and grace-end instants as computed at verification**, the verification
instant, a fingerprint of the document verified, and which accepted key verified it.

Storing the expiry and grace end as decided-at-verification instants — rather than deriving grace from
when an error happened — is what makes the brief's "an operational verification error uses the stored
claims without extending their recorded expiry or grace" true rather than aspirational. A deployment
that errors on every verification cannot renew its own grace, because nothing on the error path writes
those columns.

**The installation is the database, not the machine.** Machine activation and seat enforcement are
non-goals, and a shared store with several hosts is the operated shape; one row keyed by the store is
the only reading that makes both work. Grace, when the licence has lapsed, is taken from the document
and defaults to the recorded thirty days when the document does not name one. It is deliberately not
a deployment setting: a grace window an operator can set is a grace window with no end.

The revocation seam is an extension point that is registered or absent. It is never consulted on the
request path, never on startup, and never on readiness — the brief's self-hosted assumption is a
deployment with no outbound network for its entire lifetime, and a revocation check anywhere on those
three paths turns that deployment into a broken one.

### 7. Audit — seven fields, no payload, and no free-form anything

`AuditEvent` carries an identity, the instant, the actor's `PrincipalId` and kind, the tenant, the
action name, the resource type and resource id, the outcome, the correlation, and the record class
(*Failure modes* below). That is the brief's list plus the actor kind and the class.

**There is no payload field, no changed-field list and no free-form detail string.**
[`platform-specification.md`](../docs/docs/platform-specification.md) lists "changed fields where
appropriate", and D5 refuses it. The brief's Audit criterion requires tests that push representative
secrets through *every audited input surface* and assert that neither values nor payloads reach the
stored record or the logs. A schema with a place to put a value is a schema where that test is a
promise about caller discipline; a schema with no such place makes the test a statement about the
type. This is the one place where deleting a specified capability is the design decision.

What remains that a caller controls is the action name, the resource type and the resource id, and
those pass through the fixed redaction boundary
([`src/SubZeroDev.Platform.Observability/Redaction.cs`](../src/SubZeroDev.Platform.Observability/Redaction.cs))
before storage. That boundary is `internal` today and is consumed by one package; D5 needs it in two
more, so **it moves to a framework package both can reach and stays non-injectable** — the D3 decision
that made it fixed rather than configurable is unchanged, and a redaction boundary a consumer could
replace is not a boundary.

The audit record is append-only at the contract: no update, no delete. **D5 selects no retention**, per
the brief's operating assumptions, so the table grows without bound and no pruning job is registered
even though [`Prune`](../src/SubZeroDev.Platform.Persistence/Prune.cs) exists. That is a real cost, it
is accepted deliberately, and the reason to state it here is that the first consumer to notice will be
an operator rather than a reviewer.

### 8. Mcp — registration and exposure are two different facts

`ToolRegistration` carries the tool's name, the producer that supplied it, its parameter schema, the
permission required to invoke it, and whether it is exposed. It is **in-memory and frozen after
startup**. Nothing registers, unregisters or re-exposes a tool at runtime.

Freezing removes an entire class of concurrency — a catalogue read racing a registration — and it makes
the two safety properties checkable at startup instead of per call. It costs the ability to install a
plugin without a restart, which is a real capability the Automator will eventually want and which is
additive when it does: a mutable catalogue can replace a frozen one, and the reverse is not true.

Registration and exposure are separate because the brief requires a registered-but-unexposed tool to be
neither listed nor callable, and because
[`second-consumer-packages.md`](../docs/docs/second-consumer-packages.md) §4 rejects automatic exposure
on install outright. Exposure is configuration, resolved at startup, default closed.

**No tool parameter may be a secret, and that is enforced at registration.** Every parameter name in
every registered schema is tested against the same fixed marker set the redaction boundary uses; a
match **fails startup with a named error**, in the shape Core already uses for a bad module graph. The
inherited rule — authentication belongs to the connection, never to a call — is a property of the
transport (*Control flow*, path 3); this is the structural half of it, and it is the half that can be
checked.

### 9. Composition profile — the value that makes "absent" checkable at runtime

`CompositionProfile` is `Local` or `Operated`, it is configuration, and it joins the settings
fingerprint. The package graph already decides what is present; the profile is what lets startup say so
out loud. `Operated` with no authentication provider registered fails startup. `Local` with an
authentication provider, a billing contributor or an organizations resolver registered fails startup —
because a local host that has grown a commercial dependency by accident should stop, not degrade.

The brief's non-goal is explicit that Identity, Organizations, Billing and Licensing are *absent* from
the local composition, "not registered checks that always pass". The seam defaults in `Local` are
therefore named local providers — the composition permission provider, the anonymous-or-`system:local`
principal, the implicit tenant, the Community entitlement baseline — and each is a thing that exists and
can be pointed at, not a stub standing in for something missing.

## Module boundaries

### 1. The placement, for every capability

The brief requires framework-versus-module placement recorded for all nine, with none left
`Undecided`. This is that table. Every framework entry is a seam — a question, a contract and a
composition point. **No framework entry contains policy**, and that is the test each one had to pass.

| Capability | Framework | Module |
|---|---|---|
| Identity | the principal contract, its four kinds, the ambient principal, the transport-authentication seam | authentication providers and principal mapping. No directory, no user table |
| Authorization | permission names, the provider seam, the evaluator, the decision type, tenant-aware evaluation | grant contributors. D5's are the composition provider and Organizations |
| Organizations | — | all of it: organizations, memberships, invitations, ownership, the tenant resolver for the active organization |
| Tenancy | the resolver seam, the ambient tenant, query enforcement, the shareable declaration and the audited shared-read scope | tenant *provisioning*, which is Organizations |
| Billing | the entitlement seam, shared with Licensing | plans, subscriptions, provider adapters, plan transitions, the provider event seam |
| Licensing | the entitlement seam, shared with Billing | verification, the durable verified-licence record, the revocation extension point |
| Audit | the event contract, the sink seam, transaction enlistment, and a default sink that writes to the log | the durable store and its query surface |
| Shared web UI | — | a separate deployable that consumes the public HTTP API |
| Mcp | — | all of it: transport, connection authentication, consent, logging, registration, exposure |

Six capabilities land wholly or partly in the module tier. Five of those six are infrastructure rather
than application concerns, which strains ADR-006's *label* without touching its rule: rule 1's
operative test is "opt-in, separately packaged, and its absence is invisible", and every one of them
meets it. Whether the ADR's vocabulary should be corrected is in *Open questions*; the placement does
not wait on the answer.

### 2. The seam-admission test

A seam enters the framework only when **a framework package must consume it on a path that exists with
every module absent, or two independent modules must consume it and cannot reach each other.** Nothing
else. Applied:

| Seam | Admitted because |
|---|---|
| Principal | Persistence stamps the actor columns on every write, with or without an Identity module |
| Tenant | Persistence filters every query, with or without an Organizations module |
| Permission | Mcp and the web shell both evaluate; neither may reach the other, and Hosting's endpoint conventions need it |
| Entitlement | Billing and Licensing both contribute; Mcp and product code both consume |
| Audit | Authorization and Tenancy write it from inside the framework; Mcp writes it from a module |

An Organizations seam fails the test — no framework package needs a membership, and no second module
consumes one — which is why Organizations is a module with no framework half at all. The test is
recorded because the pressure runs one way: every future capability will have a reason why *its*
contract would be convenient in Abstractions, and a framework that accumulates seams for capabilities
nobody installed has become the twenty-four-package plan by increments, which
[`minimal-platform-packages.md`](../docs/docs/minimal-platform-packages.md) §1 names as the exact
hazard the guard exists against.

**The cost, stated.** The framework's public surface grows by five contracts that a consumer taking no
module never uses, and each carries the generated-reference obligation ADR-006's consequences already
name. That is the price of rule 2 being vacuous rather than merely observed, and it is cheaper than the
alternative it replaces — see *Alternatives considered*, § **Audit as a module**.

### 3. What each unit owns, depends on, and exposes

Framework packages are the six of
[`minimal-platform-packages.md`](../docs/docs/minimal-platform-packages.md). D5 adds to three of them
and leaves three untouched in kind.

- **Abstractions** gains the principal, permission, entitlement and audit contracts and the composition
  profile. Depends on nothing, as before. Exposes contracts only; it acquires no implementation, which
  is the property that lets a consumer compile against it alone.
- **Core** gains the provider registries — permission providers, entitlement contributors, tenant
  resolvers, audit sinks, authentication providers — and the startup validation that checks a
  registered set against the declared composition profile. Depends on Abstractions. Touches no network,
  database or filesystem, unchanged.
- **Hosting** gains the fixed request order (*Control flow*, path 1): authentication, then tenant
  resolution, then the operation scope, then authorization at the endpoint convention. Depends on Core
  and Abstractions. It knows no product concept, and it knows no capability — it knows the seams.
- **Persistence** gains the shareable declaration, the widened filter and the shared-read scope, and it
  gains the audit sink's transaction enlistment. Depends on Abstractions. The tenant column, keys and
  implicit constant are unchanged.
- **Observability** gains nothing except that the redaction boundary moves out of it, to Abstractions,
  so Audit and Mcp can reach the same one. This is the only change D5 makes to a settled D3 decision,
  and it changes where the boundary lives, not what it does.
- **Testing** gains fakes for the framework seams only: a fake principal of each kind, a fake tenant
  resolver, a fake entitlement contributor, an audit inspector, and the composition profile. It gains
  no fake organization, subscription or licence — those are module knowledge, and a framework package
  faking one would be rule 1 violated by the test helpers, which is where it is least likely to be
  noticed. Each module carries its own fakes.

Modules, each depending only on framework packages:

- **Identity** owns authentication providers and the mapping from an authentication result to a
  `Principal`. Exposes registration. Owns no rows.
- **Organizations** owns organizations, memberships, invitations and the tenant it provisions per
  organization. Exposes the organization API, a tenant resolver and a permission provider. Depends on
  the framework's principal and tenant contracts; it has no knowledge of Identity, and none of Billing.
- **Billing** owns plans, subscriptions and provider adapters. Exposes an entitlement contributor, an
  administration API and the provider event seam. Scoped by tenant, so it needs nothing from
  Organizations.
- **Licensing** owns verification and the verified-licence record. Exposes an entitlement contributor
  and the revocation extension point.
- **Audit store** owns the audit table and its query surface. Exposes an audit sink and a read API.
- **Mcp** owns the transport, connection authentication, the tool catalogue and invocation. Exposes tool
  producer registration and exposure configuration. Consumes the principal, permission, entitlement and
  audit seams.
- **Web shell** owns nothing on the server. It consumes the public HTTP API over the network.

### 4. Dependency direction

```text
                       Abstractions
                            ↑
              ┌─────────────┼─────────────┬──────────────┐
             Core      Persistence   Observability     Testing
              ↑             ↑
              └──── Hosting ┘
                            ↑
   ┌──────────┬─────────────┼───────────┬──────────┬───────────┐
Identity  Organizations  Billing   Licensing  Audit store    Mcp
                            ↑
                    (HTTP, not a reference)
                            │
                       Web shell
```

Every arrow points up. **No module appears on any other module's path**, which is rule 2 discharged
structurally rather than by review. The graph is acyclic: framework packages form the D3 graph
unchanged, modules are leaves, and the web shell is not in the graph at all — it reaches the system
over the network, which is what makes "backend packages build and run with no reference to the UI
package" provable by the build rather than asserted.

### 5. What enforces it

Three checks, and the brief requires all three to exist before D5 is complete.

1. **A framework package referencing a module fails the build.** ADR-006's consequences name this as the
   cost most likely to be paid silently, and note that without the check the ADR is a preference. It is
   an architecture test over the resolved package graph, and it has to fail against a deliberately
   broken graph before it counts — the same standard
   [`minimal-platform-packages.md`](../docs/docs/minimal-platform-packages.md) §2 sets for the provider
   contract tests.
2. **A module referencing a module fails the build.** Same test, second direction.
3. **A reference to subscription state from outside Billing fails the build**, which the brief names
   explicitly under its Billing criterion.

The local host's package graph is the fourth check and it is the brief's own: the local host must have
no package or project reference to Identity, Organizations, Billing or Licensing, and that is an
assertion over its dependency graph rather than a runtime probe.

## Control flow

### Path 1 — an inbound request reaches an operated host

The order is fixed, and it is the most expensive thing in this document to change later, because every
capability's semantics are stated relative to it.

1. **Authenticate at the transport.** An authentication provider produces a `Principal`, or produces
   none and the principal is `Anonymous`. Failure to *validate* a presented credential is not the same
   as presenting none: a bad token is rejected here with a stable code, and an absent one continues as
   `Anonymous` to be denied later by authorization, if it is denied at all.
2. **Resolve the tenant.** Registered resolvers run in order; the first that answers wins; none
   answering means `TenantId.Implicit`. In the operated sample the answering resolver is Organizations,
   reading the request's active-organization selection and confirming the principal's membership.
3. **Open the operation scope**, carrying correlation, tenant, principal, trace and culture, through the
   existing factory in
   [`src/SubZeroDev.Platform.Abstractions/OperationContext.cs`](../src/SubZeroDev.Platform.Abstractions/OperationContext.cs).
   The scope's tenant and principal are fixed for the request's lifetime. A membership revoked while the
   request is in flight does not change the request that already resolved.
4. **Authorize.** The evaluator asks every permission provider for the named permission, in the resolved
   tenant, against the resource when the check is resource-scoped.
5. **Check entitlement**, if the endpoint is gated by a feature.
6. **Do the work**, inside a transaction when it writes.
7. **Audit**, per the class rules in *Failure modes* below.

**Authorization precedes entitlement, and both precede any side effect.** The order is not arbitrary. A
principal who may not perform an action must not learn from the response whether the deployment is
entitled to the feature, and entitlement resolution may read the store while an authorization denial
must not. Reversing them turns every entitlement into an unauthenticated probe.

**Tenant resolution precedes authorization** because permissions are tenant-aware — the brief's
Authorization row requires it — and a decision taken before the tenant is known has been taken in the
wrong tenant.

**The same path in the local host is the same path.** No step is skipped and no branch is taken. Step 1
finds no authentication provider and produces the `system:local` `System` principal or `Anonymous`
depending on how the host exposes the endpoint; step 2 finds no resolver and answers `Implicit`; step 4
asks the composition provider, which grants; step 5 asks a contributor set that contains only the
Community baseline. The absence of the four commercial packages is visible in the graph and invisible
in the flow, which is the property the brief asks for when it refuses "registered checks that always
pass".

**The shared-resource branch.** A read that needs another tenant's published rows opens the shared-read
scope for one declared type, which emits one audit event, and closes it. Every read outside that scope,
on the same request, is tenant-scoped as normal.

### Path 2 — a host starts

Startup is where D5 turns composition into a checked fact, and it uses Core's existing convention: a bad
graph fails at startup with a named error rather than at first use.

1. **Modules register**, in topological order, through the existing module contract.
2. **The provider registries close.** Permission providers, entitlement contributors, tenant resolvers,
   audit sinks and authentication providers are enumerated and frozen.
3. **The composition profile is validated against them.** `Operated` with no authentication provider
   fails. `Local` with an authentication provider, an entitlement contributor other than the Community
   baseline, or a tenant resolver fails. The failure names the profile, the offending registration and
   which of the two it disagrees with.
4. **Permission names are collected** from every contributing module and checked for duplicates across
   modules — two modules claiming the same name is a composition defect, not a last-writer-wins.
5. **Tool schemas are validated**, when Mcp is present: a parameter name matching the sensitive marker
   set fails startup, and so does a tool whose required permission is not a registered name.
6. **Licence verification runs once**, when Licensing is present. Its outcome writes the verified-licence
   record or leaves the stored one untouched, and it never fails startup — a deployment that cannot
   verify a licence starts, degrades, and continues at its last known tier, per
   [`tenancy-billing-licensing.md`](../docs/docs/tenancy-billing-licensing.md), *Enforcement rules*.
7. **The settings fingerprint is computed**, now including the composition profile and the contributor
   set, so a second instance registering a different set is visible through the existing
   `platform.settings-fingerprint` health check rather than through divergent behaviour.

Steps 3, 4 and 5 are the ones that make the design's guarantees structural. Each is a startup failure
because each describes a deployment that would otherwise run and be wrong quietly.

### Path 3 — an MCP client invokes a tool

1. **The connection authenticates.** A `Principal` is established for the connection's lifetime and does
   not change; re-authenticating means a new connection. Every credential exchange happens here and
   nowhere else, which is the structural form of the inherited rule that a secret is never a tool
   parameter — an argument reaching a tool has already entered the model's context, and a credential a
   model has seen is disclosed.
2. **The tool is looked up in the frozen catalogue.** Unregistered and registered-but-unexposed are the
   same answer: unknown tool. Not "forbidden", which would confirm it exists.
3. **The tenant resolves** from the connection's principal, by the same resolvers path 1 uses.
4. **Authorization runs** for the tool's declared permission, before invocation and before any argument
   is interpreted.
5. **Entitlement is checked**, when the tool declares a feature.
6. **The tool is invoked**, inside an operation scope of its own, so a long-lived connection's many calls
   are separately correlated.
7. **The invocation is audited** — actor, tenant, tool as the action, outcome — with no arguments, which
   the audit schema makes structural rather than a rule the Mcp module has to remember.

## Failure modes

### External dependencies

**The database (SQLite or PostgreSQL).** Unreachable is already covered by `platform.database` and the
existing startup check; D5 adds no new detection. What D5 adds is the consequence for each seam:
authorization providers that read the store fail closed, so an unreachable store denies rather than
grants; entitlement contributors reading the store fail *closed for new grants and open for stored
claims* — Billing's contributor cannot answer and contributes nothing, Licensing's answers from the
record it read at startup and holds in memory. A denial from an unreachable store returns a retryable
error code, because a caller who retries after the store returns is right to. State left behind: none.

**The token issuer's key material.** A provider validating bearer tokens needs signing keys, and
fetching them is a network call. Keys are fetched at startup and cached; a request arriving when no key
is cached is rejected as unauthenticated with a stable code, **never as a server error**, and never by
blocking the request on a fetch. Retry: nothing on the request path — Platform retries nothing there,
and `PlatformError.IsRetryable` is the caller's signal, not an instruction Platform follows itself.
This is also the boundary where the local shape's guarantee is kept: with no authentication provider
there is no key material and no fetch, so an offline local host has no failure here to have.

**The licence file.** Four outcomes, and they are deliberately distinguishable in the record and the
log even though three of them fall back identically:

| Outcome | Meaning | Effect |
|---|---|---|
| `Verified` | signature valid against an accepted key, payload well formed | writes the verified-licence record, subject to the monotonic guard |
| `Invalid` | signature fails, wrong key, malformed payload | the document is ignored **entirely**; never grants a tier; logged loudly and audited once |
| `Unavailable` | absent, unreadable, I/O error | stored claims stand; logged; audited once |
| `ClockUnusable` | the clock reads earlier than the stored verification instant | evaluated at the stored verification instant; logged; audited once |

`Invalid` and `Unavailable` are the same fallback and different diagnoses, and collapsing them was
rejected: an operator seeing "licence unavailable" reaches for the file, and one seeing "licence
invalid" reaches for the key, and a single code sends both to the wrong place. Fallback in every case
is the stored record if one exists, Community if none does — the brief's "a fresh installation with no
verified claims continues at Community tier" is the second half of that sentence, not a separate rule.

`ClockUnusable` deserves its own row because a backwards clock is the one input that can make expiry
and grace produce a *worse* answer than not evaluating at all. Evaluating at the stored verification
instant neither extends grace nor expires early, which are the two ways to be wrong. D5 detects and
logs it; it does not claim to resist an operator who controls the machine, per the brief.

Each of these is audited **once per detection, not once per check.** An expired licence checked on every
request would otherwise write an audit record per request, which is a denial-of-service against the
audit trail delivered by the audit trail.

**A billing provider.** Never reached on the request path, at startup, or on readiness. Its events are
inbound, and a redelivered event is idempotent through the recorded event identity. A provider that
stops delivering leaves the subscription at its last known state, which is the same failure mode as a
lapsed subscription and is handled by the same expiry rules — features degrade, data and running work do
not.

**A revocation service.** Optional, absent by default, never consulted on startup, readiness or feature
use. Unreachable is not a failure mode because there is no path on which it is required.

**The MCP client's transport.** A dropped connection ends the connection's principal; in-flight
invocations are cancelled through the existing cancellation plumbing. Nothing is left half-applied that
a transaction would not already have rolled back.

**The web shell's backend.** The shell holds no state the backend does not, so an unavailable backend
renders an error and nothing is lost. The shell must not acquire a privileged endpoint of its own; the
brief requires organization switching to go "through the same backend API used without the UI", and an
admin-only endpoint that only the UI calls is the specific thing that makes a replaceable shell
unreplaceable.

### Boundaries

**Existence is not confirmed to a caller who may not see it.** A cross-tenant read returns *not found*,
never *forbidden*, because forbidden confirms the resource exists. Switching to an organization the
principal is not a member of returns not found for the same reason. A permission denial on a resource
the principal *can* see returns forbidden, because there the existence is already known and pretending
otherwise only obscures the fix. These two answers are not interchangeable and the difference is a
security property, not a style choice.

**Audit and the transaction.** The rule has two halves and they cover the whole space:

- **A successful action that wrote state writes its audit row in the same transaction as the state
  change.** Atomic in both directions: no committed change without its audit row, and no audit row for a
  change that rolled back. This is the existing outbox pattern — enqueue requires an ambient transaction
  ([`Results.cs`](../src/SubZeroDev.Platform.Abstractions/Results.cs), `NoAmbientTransaction`) — applied
  to a second writer.
- **A denial, a read, or a failure that wrote nothing writes its audit row in its own transaction,
  after the outcome is known.** There is no action transaction to join, and a failure that rolled back
  is precisely the thing that must still be recorded.

A failure of the first kind rolls the action back, which needs no idempotency and no reconciliation. A
failure of the second kind has nothing to roll back, and the record's **class** decides what happens:

| Class | On audit-write failure | Which actions |
|---|---|---|
| `Required` | the response becomes a retryable failure, and readiness degrades | authorization denials, shared-resource escapes, membership and ownership changes, entitlement and licence transitions, MCP invocations |
| `Recorded` | logged, readiness degrades, the response is unaffected | everything else |

A single class was rejected in both directions. All-`Required` means an audit outage is a total outage,
which is the self-inflicted outage
[`tenancy-billing-licensing.md`](../docs/docs/tenancy-billing-licensing.md) refuses elsewhere.
All-`Recorded` means the brief's "allowed, denied and failed actions persist" is true only when nothing
is wrong, which is not what a security control is for.

**Partial failure in organization creation.** Creating an organization mints a tenant, writes the
organization and writes the owner's membership. All three are one transaction, and the audit row joins
it. There is no window in which an organization exists without an owner, and none in which a tenant is
minted for an organization that failed to be created.

**Partial failure in invitation redemption.** Redemption is a single conditional update against the
unredeemed state, so a token presented twice creates at most one membership. The second attempt reports
the invitation already redeemed. An expired invitation reports expired, and neither answer distinguishes
a token that never existed from one that did — an invitation token is a capability, and a probe that
tells the prober which guesses were close is a capability oracle.

**Startup failures.** Every check in path 2 fails the host rather than degrading it, and each names the
registration that caused it. A host that cannot state its own composition should not serve, because
every guarantee in this document is stated relative to a composition.

**The shared-read scope.** A write attempted inside it throws rather than returning an error, because it
is a defect in the caller and not a runtime condition — the distinction
[`Results.cs`](../src/SubZeroDev.Platform.Abstractions/Results.cs) already draws. A scope left open by a
caller that failed to dispose is bounded by the operation scope's own lifetime: the request ends, the
ambient context is restored, and the next request does not inherit it.

**What state is left behind, in summary.** Nothing in D5 leaves a half-applied write. Every state change
is transactional; the only records written outside their action's transaction are audit rows for actions
that changed nothing; the licence record is a single-row monotonic write; and the tool catalogue is
in-memory and frozen. The one durable thing that grows without bound is the audit table, deliberately.

## Concurrency and ordering

**Within one request, nothing is concurrent.** The operation scope is ambient and single-threaded for a
request's lifetime, and the fixed order of path 1 is what enforces it. The tenant and principal are
resolved once and cannot change; a membership revoked mid-request affects the next request.

**Across instances, four things are genuinely concurrent**, and the operated proof runs its contention
scenarios on PostgreSQL because SQLite is a single-node provider.

| Concurrent | What must not happen | Enforced by |
|---|---|---|
| Several hosts verifying the same licence document | an older verification overwriting a newer one, so a replaced document is undone by a host still holding the old file | one row per installation, written only when the incoming verification instant is later than the stored one; every host reads *the stored record*, not only its own file, so all hosts converge on the newest document |
| Two organizations being created | two organizations sharing a tenant | uniqueness on the organization's tenant column; the mint and the write are one transaction |
| One invitation redeemed twice | two memberships from one token | a conditional update against the unredeemed state — at most once, by the store |
| Audit rows from every host | nothing; appends do not contend | append-only, no unique key across hosts |

**Audit ordering is deliberately weak, and that is stated so nobody relies on the opposite.** Audit rows
carry an instant from `IClock` and a correlation, and they are *not* totally ordered across hosts. Two
hosts with skewed clocks can write rows whose stored order disagrees with real time. Building a total
order would need a sequence every host contends on, which is a write bottleneck on the path every
security-sensitive action takes. Correlation is what makes a trail reconstructible, and it is the thing
the design guarantees; a global ordering is not.

**Entitlement is evaluated at admission and carried, not re-evaluated during execution.** A unit of work
that was accepted or scheduled carries the entitlement decision that admitted it, and nothing re-checks
it while it runs. This is what makes the brief's "after the grace period, new paid-feature work is denied
while accepted, running and scheduled work continues" a property of the design rather than a behaviour
to be arranged case by case, and it is why an entitlement decision is a value that can be persisted with
a work item rather than only a function call.

**The tool catalogue is immutable after startup**, so there is no registration-versus-invocation race to
resolve, and no lock on the path every MCP call takes.

**Background work is unchanged.** The existing lease
([`src/SubZeroDev.Platform.Persistence/Lease.cs`](../src/SubZeroDev.Platform.Persistence/Lease.cs))
still decides which instance runs a single-runner registration, and D5 adds no background work of its
own: no retention job, no revocation poll, no licence re-verification timer. Licence state changes when
a host restarts or when a host is asked to re-verify; a timer that re-verifies would be a second writer
contending on the one row for no requirement anybody stated.

## Alternatives considered

### 1. Audit as a module, with the framework knowing nothing about it

**Chosen:** the audit *contract*, the sink seam and the transaction enlistment are framework; the
durable store and its query surface are a module; the default sink with no module installed writes to
the log, through the redaction boundary that is already there.

**Rejected:** Audit as a module in full, which is what the extraction guard's usual answer would be —
Audit has no divergence analysis in
[`second-consumer-packages.md`](../docs/docs/second-consumer-packages.md) and no row in
[`platform-identity.md`](../docs/docs/platform-identity.md) §4, so it is one of the four the brief
admits by decision.

**Why:** Authorization denials and shared-resource escapes are audited from *inside framework
packages*, and Mcp audits from a module. A module-only Audit makes the first a framework-to-module
reference (rule 1, a build failure) and the second a module-to-module reference (rule 2). There is no
arrangement of a fully-modular Audit that satisfies both rules while the framework itself has anything
to record, and the framework does. Splitting the contract from the store is the only shape that keeps
both rules and keeps the brief's local-mode `system:local` actor working with no audit package present.

**Reversibility: cheap.** The framework half is a record, a sink interface and an enlistment rule. If
Audit turns out not to belong in Platform, the store module moves to its one consumer and the framework
loses three types, not a subsystem — which is the reversibility the brief asks be preserved for the four
evidence-free capabilities.

### 2. One entitlement seam, or separate billing and licence queries

**Chosen:** one `FeatureName` question, contributed to by Billing and Licensing as registered
contributors, resolved as a union, with the decision naming its source.

**Rejected:** two queries — "is the subscription active" and "does the licence grant this tier" —
which is the shape both capabilities' own documents describe and which needs no new concept.

**Why:** the brief requires product code to consume entitlements and never subscription state, and
[`tenancy-billing-licensing.md`](../docs/docs/tenancy-billing-licensing.md) forbids any code path
outside the billing module branching on it. Two queries reintroduce that branch under a different
name — every gated feature would ask which commercial model is in play — and they make the self-hosted
and operated shapes structurally different at every call site rather than at composition.

**Also rejected: intersection rather than union.** Requiring every contributor to grant would mean
installing Licensing into an operated deployment silently revokes subscription entitlements. That is a
failure nobody would look for, because it presents as a working system denying a feature the customer
paid for.

**Reversibility: expensive.** This is the public shape product code is written against. Changing it
later rewrites every call site in every consumer, which is why it is settled here rather than at
`/contract`.

### 3. The shared-resource escape — an audited read scope, a per-row flag, or a cross-tenant permission

**Chosen:** shareability declared on the entity type at model build; publication as an ordinary
tenant-scoped write by the owner; cross-tenant reads only inside a named, audited, read-only scope
that widens the filter for one declared type.

**Rejected: a per-row `IsShared` flag with the query filter honouring it globally.** Simplest, and it
is how the feature is usually built. Rejected because it makes the isolation boundary writable by every
code path that can write the row, and because a filter that always honours the flag means no caller ever
states that it intends a cross-tenant read — so there is nothing to audit and nothing to grep, which is
the "unmodelled escape" [`second-consumer-packages.md`](../docs/docs/second-consumer-packages.md) §3
names as how isolation quietly stops holding.

**Rejected: a `Platform.Tenancy.ReadAcrossTenants` permission and no scope.** Auditable and explicit,
and it fits the authorization model already being built. Rejected because a permission is held for a
session, not for an operation: a principal holding it reads across tenants for every query it makes,
including the ones nobody intended, and the audit record says a principal *could* have crossed rather
than that it *did*.

**Rejected: allowing writes inside the scope.** Symmetry, and it would let a shared resource be edited
by a collaborator. Rejected because "there is no path by which a write reaches another tenant's row" is
a far stronger invariant than anything the symmetric version buys, and the Game Engine's published
campaigns — the consumer that forced this design — are read across tenants and written by their owner
only.

**Reversibility: expensive** for the write half, cheap for the rest. Widening reads later is additive;
admitting cross-tenant writes later is a change to an invariant other code will have come to rely on.

### 4. An organization holds a tenant, or an organization *is* a tenant

**Chosen:** one organization has exactly one tenant, minted with it and held as a column on the
organization. The framework never learns that a tenant has an owner.

**Rejected:** making the organization id the tenant id. One fewer column, one fewer join, and no
possible disagreement between the two. Rejected because it puts a module's identity into a framework
type: `TenantId` would then mean "an organization", the framework would carry a module's concept in its
most load-bearing value, and a consumer wanting more than one tenant per organization — which none has
asked for and which is plausible for a studio with several white-label properties — would face a
migration on every table rather than an added row.

**Rejected:** organizations and tenants as orthogonal dimensions. Maximum flexibility. Rejected because
no consumer needs it, nothing in the brief exercises it, and generality invented without a consumer to
test it is the failure [`second-consumer-packages.md`](../docs/docs/second-consumer-packages.md) §1
describes and [ADR-006](../docs/docs/adr/ADR-006-application-modules.md) rejects by name.

**Reversibility: cheap.** The one-to-many case is an added table and no change to the framework.

### 5. A total principal, or the nullable one that exists today

**Chosen:** the ambient principal is non-null, with `Anonymous` as a well-known value, exactly as
`TenantId.Implicit` is a well-known tenant. `ClaimsPrincipal?` stays alongside it as the raw
authentication result for consumers that want claims.

**Rejected:** keeping the nullable principal and letting audit record an empty actor. No change to a
published 0.x surface, and the null already means what it means.

**Why:** a null actor is indistinguishable from an actor that was never resolved, so an audit trail
containing them cannot answer the question it exists to answer. The brief requires allowed, denied and
failed actions each to persist an actor, and a nullable type makes that a convention rather than a
property. Doing it now costs a breaking change to packages the brief already describes as explicitly
unstable 0.x; doing it after a consumer ships costs the consumer.

**Reversibility: expensive**, which is the argument for taking it now rather than later.

### 6. Audit with no payload, against the specification's "changed fields where appropriate"

**Chosen:** seven fields plus the actor kind and the class. No payload, no changed-field list, no
free-form detail. The three caller-controlled strings pass through the fixed redaction boundary.

**Rejected:** the specification's list, including changed fields. It is the specified shape, it is what
an auditor usually asks for, and "we redact it" is the standard answer.

**Why:** the brief's Audit criterion requires tests that push representative secrets through every
audited input surface and assert nothing reaches the record or the logs. With a payload field, that test
asserts a property of the redaction rules and of every caller's discipline, forever, including callers
that do not exist yet. Without one, it asserts a property of the type. Deleting the capability is what
makes the criterion checkable, and a changed-field list is the single most likely place for a credential
to arrive by accident, because the field that changed is often the one that matters.

**Reversibility: cheap in the wrong direction and that is the point.** Adding a payload later is easy
and should be resisted; the cost of having refused it is that a consumer wanting field-level change
history builds it in its own tables, where the secret question is theirs.

### 7. Entitlement at admission, or entitlement at each step

**Chosen:** a unit of work carries the entitlement decision that admitted it; execution does not
re-check.

**Rejected:** re-evaluating on each step, which is more current and is what a naive reading of "gate the
feature" produces.

**Why:** the brief and
[`tenancy-billing-licensing.md`](../docs/docs/tenancy-billing-licensing.md) both require that expiry
degrades features and never touches running or scheduled work, and that a player mid-session does not
lose it. Re-evaluation makes that behaviour depend on where the expiry lands relative to a step
boundary, which is a race, and it puts an entitlement read on every step of every background job.
Deciding once at admission makes the guarantee structural.

**Reversibility: expensive.** It decides whether an entitlement decision is a value or a call, and the
work item's persisted shape follows from the answer.

### 8. `Platform.Mcp` freezes its catalogue at startup

**Chosen:** tools register and are exposed at startup; the catalogue is immutable afterwards.

**Rejected:** a mutable catalogue supporting registration at runtime, which the Automator will
eventually want so a plugin install does not need a restart.

**Why:** freezing lets both safety properties — no secret-shaped parameter, and default-closed
exposure — be checked once at startup with a named failure, rather than on every registration with a
runtime error nobody sees. It also removes a catalogue-mutation-versus-invocation race from the path
every MCP call takes.

**Reversibility: cheap, and only in the useful direction.** A mutable catalogue can replace a frozen one
without changing any consumer, and the startup checks become registration-time checks. The reverse —
freezing a catalogue consumers have learned to mutate — is not available.

### 9. Building the tenancy and identity substrates, against adopting existing ones

[ADR-004](../docs/docs/adr/ADR-004-framework-build-not-adopt.md) §4 requires each gap to be checked
against existing packages before anything is written, and the reason recorded either way.
[`minimal-platform-packages.md`](../docs/docs/minimal-platform-packages.md) §3a already made two
recommendations that point directly at this stage, and both are answered here.

**Finbuckle.MultiTenant — recommended there for exactly this stage, and rejected here.** That document's
words were "EF Core query filters now; adopt Finbuckle when tenancy becomes a feature", and D5 is when
tenancy becomes a feature, so this needs a reason rather than a preference. Two:

- The brief's non-goals forbid redesigning the settled tenant identifier, primary keys or
  implicit-tenant storage representation. Finbuckle brings its own tenant-info model and its own
  resolution and store abstractions, and adopting it means re-homing a shape D3 settled and G2 built on.
- The part of D5's tenancy that is actually hard is the deliberately shared resource, and that is the
  part no multi-tenancy library provides — a declared-shareable type, an audited read-only escape scope,
  and the invariant that no write crosses a tenant. Adopting the library would leave the hard half to be
  written anyway, on top of a model this repository did not choose.

What the library's *resolution strategies* — host, header, claim — are worth is as a design reference,
and the resolver seam is deliberately shaped so that a Finbuckle-backed resolver could be registered by
a consumer without Platform depending on it.

**Supabase as an identity substrate — not rejected, and not chosen.** That document recorded it as a
live option for D5. The brief's non-goals settle it: choosing or operating an identity substrate is out
of scope, and D5 defines provider-neutral seams. Supabase's OIDC server therefore becomes a *deployment*
choice behind the authentication seam, which is what the recommendation "decide neither now" wanted and
what `AGENTS.md`'s "depend on the protocol, not the vendor" requires. No dependency is taken and none is
foreclosed.

**Token validation is in-box.** An OIDC or JWT bearer provider needs the ASP.NET Core authentication
handlers that ship with .NET; no third-party package is required for the authentication seam's first
provider.

**Licence signature verification is in-box.** Asymmetric signature verification over a signed document
is `System.Security.Cryptography`. The design needs no licensing library, and taking one would mean
adopting its document format as Platform's public licence format.

**Key handling, decided here because it is a public contract.** Platform is not a licensor: the accepted
public keys are supplied by the consuming product, not compiled into Platform. A deployment accepts an
*ordered set* of public keys rather than one, so key rotation does not need a flag day, and the verified
record names which key verified the document.

**One evaluation is outstanding and is deliberately not guessed at:** whether `Platform.Mcp` adopts an
existing MCP protocol implementation or implements the transport. It is in *Open questions*, because
taking a dependency is a decision with an authorization requirement, and because asserting a package's
licence and capabilities from memory is exactly what `AGENTS.md`, *Verification*, forbids.

## Open questions

These are the four things this design could not settle from the brief, the tree, or a decision already
logged. Each carries a recommendation, recommended option first.

### 1. Does `Platform.Mcp` adopt an existing MCP implementation, or implement the transport?

This blocks `/contract`, because the answer decides whether the tool registration and invocation
contracts are Platform's own types or a projection of somebody else's.

**Recommendation: evaluate before deciding, and treat the evaluation as a gate on `/contract` rather
than something this document assumes.** What has to be established is the licence and its durability —
[`minimal-platform-packages.md`](../docs/docs/minimal-platform-packages.md) §3a's finding that three
foundational .NET libraries changed licence within one year is the reason durability is a first-class
criterion here — whether the implementation separates transport from tool *production*, since a package
that assumes it owns tool definitions cannot serve the two-producer requirement that put Mcp in this
brief at all, and whether connection-level authentication is expressible.

The alternative is implementing the transport, which is more work and is guaranteed to fit. It becomes
the answer if the evaluation finds any implementation that bakes in a single tool-definition producer,
because that is the designed-from-one-consumer failure arriving through the door the guard was watching.

Either way this needs a decision-log entry naming what was rejected, per `AGENTS.md`, *Hard rules*.

### 2. How is the shared administration shell delivered?

The brief requires a replaceable shell that consumes the same backend API a caller uses without it, and
backend packages that build with no reference to it. That leaves the delivery shape open, and it sets a
public contract and an information-architecture direction, which `AGENTS.md`, *Working with me*, says to
ask about rather than assume.

**Recommendation: a separate front-end build, served as static assets by whatever host chooses to serve
it, with no server-side rendering and no .NET package the backend could reference.** It makes "no
backend reference" provable by the build rather than by review, it keeps the shell replaceable by
something the consumer writes, and it is the only shape where "the UI uses the public API" cannot quietly
become false.

The alternative is a .NET-hosted UI shipped as a package. It composes more easily for a consumer who
wants the shell with one registration call, and it makes theming and localization share the backend's
infrastructure. It is rejected in the recommendation because the reference it needs is the one ADR-006's
rule 1 exists to prevent, and because every admin-only convenience endpoint it acquires is a step away
from replaceable.

### 3. Should ADR-006's vocabulary be corrected, given what now lands in its module tier?

Six D5 capabilities land in the module tier, and five of them — Identity, Billing, Licensing, Mcp, the
audit store — are infrastructure rather than application concerns. ADR-006's *rule* is structural and
they all satisfy it; its *label*, "application module", now covers things it was not written for.

**Recommendation: amend ADR-006 with a note rather than a new tier.** The rule that matters is "opt-in,
separately packaged, absence invisible", and it is doing its job; adding a third tier would need rules 1
and 2 restated for it, which is where two-tier reasoning becomes three-tier drift. A note recording that
the tier is defined by the structural test and not by the word "application" costs nothing and keeps one
rule.

The alternative is a third tier — optional infrastructure, distinct from optional application modules.
It is more honest about what these packages are, and it would let the two kinds have different rules
about depending on each other. It is rejected in the recommendation because nothing in D5 needs that
difference, and a tier introduced before a rule needs it is a tier that will acquire one.

This is an ADR amendment and therefore the repository owner's, not `/design`'s. The placement in
*Module boundaries* does not wait on the answer.

### 4. Do the D5 packages version and release independently of the framework's 0.x, or in lockstep?

ADR-006's consequences name "two release cadences, and a version matrix" as real packaging work that did
not exist when Platform was six packages shipping together. D5 makes it six more, and the brief requires
versioned 0.x packages packed in CI and consumed by the sample from package artifacts rather than
project references — so the matrix is exercised by D5's own proof, whichever answer is taken.

**Recommendation: lockstep for the whole of D5, and revisit when the first module has a consumer the
framework does not.** While every module and the framework are built and released by one repository at
0.x, independent versioning buys nothing and costs a compatibility matrix that has to be tested. Lockstep
is a decision that unwinds cheaply — packages can diverge later, and packages that have diverged cannot
easily be brought back.

The alternative is independent versioning from the start, which is more honest about what a module
library is and avoids a later transition. It becomes the right answer as soon as a module ships on a
cadence the framework does not, which is a question about consumers rather than about packaging.
